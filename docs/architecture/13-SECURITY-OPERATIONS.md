## 2. Credential encryption, least privilege, egress, rotation

- **Envelope encryption** with AEAD and context binding (Part 6 §3.2). KEKs per org tenant; key rotation annually or on incident (rewrap DEKs lazily on read + background job).
- **Database least privilege**: roles `app_rw`, `worker_rw`, `broker_rw`, `ops_ro`, `migrator`; only `broker_rw` can select `creds.secret_versions`; column-level revoke for `ciphertext` from all others; RLS FORCE.
- **Service identities**: workload identity per process type; KMS decrypt permission only for `broker`; E2B API key only for `orchestrator`; Anthropic key only for `model-gateway`.
- **Network**: trusted zone in separate subnet/namespace; ingress to gateways only on their public listeners (ticket-authenticated); Broker reachable only from trusted-zone services and the OAuth callback route on the edge; default-deny egress from all processes except declared destinations (provider APIs per adapter, E2B API, Anthropic API).
- **Rotation**: platform secrets (E2B, Anthropic, email, DB passwords) rotated quarterly with dual-key overlap; tenant-provided keys rotated by owners (Part 6 §3.3) with expiry reminders.
- **Memory hygiene**: Broker and gateways avoid core dumps (`ulimit -c 0`, `PR_SET_DUMPABLE=0`), no swap on nodes, debug endpoints disabled in production.

## 3. Prompt injection and untrusted Skills/MCP servers

| Layer | Control |
| --- | --- |
| Inputs | Retrieved/tool content wrapped and labeled untrusted; system prompt tells the agent such content cannot change instructions |
| Capabilities | Tool list fixed per agent version; tickets scoped; no credential-bearing parameters in tool schemas; upstream URLs fixed |
| High-risk actions | Approval gates (sending external messages to new recipients, deleting data, financial operations, sharing outside tenant); approvals bound to argument digest |
| Exfiltration paths | Sandbox egress only to gateways; gateway destination rules; web_fetch tool blocks private IPs and limits methods to GET in R1 |
| Third-party MCP servers | Admin-installed only; tool descriptions reviewed/pinned (hash) to detect "rug-pull" description changes; responses size-limited and labeled; servers cannot receive WorkX tickets (tickets terminate at the Gateway) |
| Skills | Curated catalog, code review, hash pinning, no secrets; Skills cannot alter tool permissions; red-team evals (`evals/red-team`) on each release |
| Output | Channel replies to group chats limited by policy (Part 8 J6); artifacts sanitized on preview (HTML/SVG) |

## 4. Safe file parsing and malware scanning

- Parser runs as a separate service with no network egress, read-only root filesystem, CPU/memory/time limits, per-request process isolation (Tika forked/pipes parsing mode ○), and limits on embedded document depth and decompression ratio.
- Upload validation: magic bytes, allow-list, size/page caps, no archives in R1, encrypted documents rejected with a clear message.
- **Malware scanning is justified** when uploaded files are shared with other members or delivered to external channels; R1 enables ClamAV scanning for shared knowledge sources and artifacts delivered externally; private uploads used only by the uploader's own tasks are scanned asynchronously (non-blocking) to limit latency.
- Office artifacts generated by agents: macro-enabled formats rejected; previews rendered server-side to PDF/images in an isolated renderer (LibreOffice headless in a sandboxed container) — never in the browser as active content.

## 6. Audit, retention, deletion, privacy, backups, DR

| Item | Default (to confirm with PO/legal, Q-10) |
| --- | --- |
| Audit events | 1 year hot (PG), export to WORM object storage for plan-defined period |
| Task events | 180 days; final messages/artifacts kept until deleted by user |
| Checkpoints | 14 days after session close |
| Retrieval logs, AI traces | 30 days (redacted) |
| Logs/traces | 14–30 days |
| Deleted resources | Soft delete 30 days → purge |
| Tenant deletion | 30-day grace → purge job across PG, object storage (incl. versions), Valkey, Langfuse, E2B (terminate), KMS (destroy tenant KEK = crypto-shred of credentials and optionally tenant-encrypted checkpoints) → completion certificate in audit |
| Backups | PITR 14 days; logical backups 35 days; deleted-tenant data ages out of backups with backup retention (documented in privacy policy) |
| DR targets | RPO ≤ 15 min, RTO ≤ 4 h (assumption) |
| Data subject requests | Export (user's personal workspace + their own content in orgs per org policy), deletion via account lifecycle; org-owned content governed by the org as controller (legal review) |

Privacy-by-design: model and embedding providers receive only content needed for the task; provider data-retention and training terms reviewed per provider; tenants informed which subprocessors process their data (Anthropic, E2B, embedding provider, email provider, cloud).

## 7. Monitoring, alerting, incident response, cost attribution

| Alert | Threshold (initial) | Runbook |
| --- | --- | --- |
| Job queue lag | p95 > 30 s for 5 min | Scale consumers; check DB |
| Attempts stuck `provisioning` | > 2 min p95 | E2B status; template health |
| Sandbox create failure rate | > 5% for 10 min | E2B incident; fail fast to users |
| Model Gateway 5xx/overload | > 2% for 5 min | Backoff, degrade, status page |
| Refresh failures for a provider | > 10% for 15 min | Provider incident; mark connections degraded |
| Canary secret detected anywhere | any | Sev-1 security incident |
| Cross-tenant isolation test failure (synthetic in prod) | any | Sev-1 |
| Egress denials spike per tenant | > 5× baseline | Possible injection/exfiltration attempt |
| Dead jobs | any new | DLQ runbook |
| Budget overrun | tenant > 100% | Auto-stop; notify owner |

Incident response: severity matrix, on-call rotation (business hours in R1 + best-effort pager for Sev-1), customer communication templates, post-incident reviews. Credential incident playbook: revoke tickets globally (bump global epoch), rotate KEK, force refresh/re-auth for affected connections, notify tenants.

Cost attribution: `usage_events` per attempt (model tokens by tier, sandbox seconds, tool calls, embedding tokens, storage bytes, delivery count) → daily rollups per tenant, agent, and user; unit costs versioned (`unit_cost_ref`) so historical reports remain explainable.

## 8. Operational access

- No standing production DB access; break-glass via approved request with time-bound `ops_ro` credentials, session recording, and audit event visible to the affected tenant's owners (configurable for org plans).
- Support "view as" is not provided; support sees metadata and redacted events only.
- CI/CD: protected branches, required reviews, signed commits (recommended), OIDC-federated deploy credentials, provenance attestations for images and the E2B template.

## 9. Regional deployment differences

| Topic | Implication | Design response |
| --- | --- | --- |
| Model availability | Claude API unsupported in mainland China/HK/Macau ✅ | Cell per jurisdiction; China cell requires a different harness/model (C-01) |
| Sandbox availability | E2B region list not verified; E2B volumes not available in APAC ◐ | No dependency on volumes; `SandboxProvider` abstraction |
| Data residency | Some customers may require in-country storage/processing (e.g., mainland China personal information rules) — requires legal review | Cells: full stack per jurisdiction; tenant pinned to a cell at creation; no cross-cell replication of tenant data |
| Channel platforms | Feishu (China) vs Lark (international) are separate platforms with separate apps/endpoints ○ | Adapter per platform domain; binding stores platform domain |
| Identity | Social logins differ by region (WeChat, Feishu login vs Google/Microsoft) | Keycloak IdP brokering per cell |
| Embeddings | Provider availability differs | Embedding Gateway with per-cell provider |
| Network | Cross-border latency and filtering | Gateways co-located with sandbox provider region; CDN per cell |
