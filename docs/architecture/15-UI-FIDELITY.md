# Part 15 — UI fidelity: preserving the prototype during migration

Status: **[PO]** The interactive prototype in `workmates-prototype/dist/` is the approved design baseline. The production frontend must reproduce it while replacing simulated behavior with real backend integration. **[PO, 2026-10-31]** Fidelity scope is the **desktop web browser**; mobile/narrow layouts are not part of acceptance (see §1.3).

This part supersedes the parts of Part 9 that would have changed the visual design or information architecture (the UI library choice and the route regrouping). Part 9 has been updated to point here.

- Acceptance viewport: **1440×900** (primary) and **1280×800** (secondary check for the `max-width:1280px` breakpoint). Both languages.

This changes product requirement PL-04 ("responsive and keyboard", P0) to keyboard-only for acceptance; recorded as decision 26 in Part 1.
- Note from the baseline run: at 390 px, 11 states could not be reached with desktop selectors because those controls live in the collapsed navigation drawer. This is expected behavior, and it is why mobile was dropped from the capture defaults.

### 2.3 Interaction conventions to preserve

- Hover-or-focus reveal of row actions (`.task-row:hover .task-more`, `.sidebar-task .icon-btn`); keyboard focus also reveals them (`:focus-within`).
- Keyboard: ⌘/Ctrl+K search, ⌘/Ctrl+Enter send, Esc closes overlays, arrow keys in menus, Tab focus trap inside dialogs, focus ring `2px solid #91b2ff` with 3 px offset.
- Form validation: required fields use the browser's native constraint bubble ("Please fill out this field"); domain validation shows inline field errors (`wx-conn-field-error`) and dialog-level errors (`wx-eco-error`, `wx-channel-error`).
- Sensitive inputs (App Secret, tokens, AES keys, webhook URLs) live only in the open dialog and are cleared on close (IN-14).
- Workspace switch closes sensitive dialogs, resets route/filters/selection, keeps per-workspace drafts in memory only, and shows a toast (SA-06).
- Execution status and delivery status are shown separately (CU-03/CU-04).
- Disabled controls: `opacity: .4; cursor: not-allowed`.
- Empty states use a shared pattern (icon + title + description, sometimes a primary action): `empty()` in `app.js`, `sw-empty`, `ws-empty`, `wx-*-empty`.

### 4.2 Reuse strategy (highest-fidelity path)

1. **Port the eight stylesheets verbatim** (`style.css`, `secondary.css`, `team.css`, `ecosystem.css`, `workspace.css`, `connection.css`, `channel.css`, `spaces.css`) into `packages/ui/styles/prototype/` and load them globally in the same order as `index.html`. React components render **the same DOM structure and class names**. Refactoring into CSS Modules or tokens is allowed later, but only behind a zero-diff visual gate (§7).
2. **Icons**: port `icons.js` (`paths` dictionary of stroke SVGs) into a `<Icon name size>` component that outputs identical SVG markup. Avatars and favicon SVGs copied as-is.
3. **No new component library.** Part 9 previously proposed Radix primitives; that is withdrawn because it changes DOM structure and styling. Dialog, popover, menu, and focus-trap behavior is reimplemented in small React hooks that reproduce the prototype's behavior (`modal()`, `popover()`, keydown handler in `app.js`).
4. **i18n**: convert `messages-*.js` (pairs `[zh, en]` per key) mechanically into `locales/zh-CN/*.json` and `locales/en/*.json` with the **same keys**; English stays the default; locale stored per user (server) with `workx-locale` fallback.
5. **Validation and state rules** in `spaces-model.js`, `connection-model.js` (fields, formats, persistence allow-list), `ecosystem-model.js` (platform/method/capability constraints), and `channel-model.js` (eligibility, retry semantics) are ported to shared TypeScript modules for client feedback **and** reimplemented server-side as the authority.
6. **Copy**: reuse all strings except the simulation disclaimers listed in D-02.

## 6. Test hook contract for the production app

To drive both implementations with one catalog (`tools/ui-fidelity/states.mjs`):

1. Equivalent controls keep the prototype's `data-action` attribute and its parameters (`data-id`, `data-tab`, `data-page`, `data-filter`, `data-stage`). This is a test contract, not styling; renaming an action requires updating the catalog in the same change.
2. Equivalent containers keep their class names (`.task-row`, `.task-more`, `.menu-item`, `.composer`, `[role="dialog"]`), which also follows from §4.2.1.
3. Test builds expose `POST /__test__/fidelity/seed` (disabled in production by build flag and network policy) that loads `fixtures/prototype-seed.json` into a fresh tenant pair (personal `personal-alex`, organization `wx-demo`), signs in the demo user "Alex", and returns a session cookie. `targets.mjs` → `web` uses it (backlog B-UI-02).
4. Clock and IDs are fixed for captures (`2026-10-30T09:00:00+08:00`); simulated delays are replaced by a deterministic fake backend mode for UI tests (tasks complete after a fixed number of streamed events).


| Step | Rule |
| --- | --- |
| Viewports | 1440×900 for every state; 1280×800 for shell, home, conversation, admin members (`--viewports desktop,laptop`) |
| Locales | `en` and `zh-CN` for every state |
| Thresholds | pass ≤ 0.5 % differing pixels; review ≤ 3 %; fail > 3 % or size mismatch. Review items are fixed or recorded as approved deviations |
| Masking | Native validation bubbles, live timestamps, streamed text in "running" states (compare structure via DOM snapshot instead) |
| Interaction checks | Each catalog state's steps must succeed on the new app (a failed step is a functional failure even if pixels match); keyboard checks: Esc closes, Tab trapped in dialogs, ⌘/Ctrl+K, ⌘/Ctrl+Enter |
| Behavior tests | Port the 73 prototype test scenarios into Playwright E2E against the real backend (`apps/web/tests/e2e`), one spec per feature ID group |
| Errors | Zero console errors and zero horizontal overflow at 1440 and 1280 |
| Accessibility | axe-core scan per state; existing violations in the baseline (e.g., D-04 contrast) are reported, not silently fixed |
| Retention | `workmates-prototype/` stays in the repo and runnable until every state in the catalog passes or has an approved deviation |

## 8. Acceptance criteria (per migrated screen)

A screen is accepted only when all hold:

1. All its catalog states (both locales, 1440×900; plus 1280×800 where listed) are **pass** or **approved deviation** in `compare` output.
2. All catalog steps for those states run on the new app (same `data-action` hooks).
3. Its prototype behavior tests (mapped feature IDs) pass as E2E tests against the real backend.
4. New states for that screen (§4.3) exist, use the listed pattern, and have their own captures added to the catalog (as `new: true` states with design sign-off rather than prototype comparison).
5. No console errors, no horizontal overflow, keyboard behaviors intact, axe scan has no new violations relative to the baseline.
6. Copy matches the prototype keys in both languages except D-02 replacements.

These criteria are added to backlog items B-06, B-08, B-12, B-13, B-14, B-16, B-17, B-19, B-21 (Part 14 §4) and to the R1 exit criteria.

### 9.2 Local procedure

1. Run §7 commands for the prototype and open `out/prototype-contact-sheet.html` to review the baseline.
2. When a production screen is implemented, run `capture:web` with `--only <state ids for that screen>`, then `compare` and the contact sheet with `--candidate` and `--diff`.
3. Attach `out/diff/summary.json` and the review HTML to the pull request; list any new entries in `approved-deviations.json` with their approval reference.

### 9.3 Codex / code-review checklist for UI changes

- Does the change alter any prototype class names, DOM structure, `data-action` hooks, or stylesheet rules without a matching approved deviation?
- Were new UI states built from the patterns in §4.3 (no new visual language, component library, colors, fonts, radii, or shadows)?
- Are both languages present for every new string, with keys following the existing naming?
- Do the catalog states for the touched screens pass `compare`, and is the summary attached?
- Is the prototype still present and runnable?
- Are simulated behaviors replaced by real API calls (no `localStorage` business data, no timers standing in for backend work)?
