# WorkX SaaS 基础产品设计

版本：0.1 · 2026-10-30

WorkX 按企业 SaaS 产品设计。租户是企业数据、配置和资源的归属边界；部门表达组织架构；用户通过成员关系加入企业并获得角色。三者不能互相替代。当前运行版本仍是单企业、本地浏览器交互原型。

## 产品对象与关系

| 对象 | 含义与关系 | 当前原型 |
| --- | --- | --- |
| 租户／企业空间 Tenant | 一家客户企业的资源边界，拥有自己的成员、伙伴、项目、知识、生态连接、审计与用量。企业空间不是飞书租户，二者需要显式关联。 | 一个演示企业，可修改名称，空间标识固定；没有跨企业切换或真实隔离。 |
| 全局用户 User | 登录身份。一个用户可以加入多家企业，在不同企业拥有不同角色。 | 尚无账号、登录、密码、身份提供方或多企业成员关系。 |
| 企业成员 Membership | 连接用户与企业，记录企业内显示名、角色、部门和状态。 | 原有 teamMembers 作为本企业成员演示，可添加、编辑姓名、角色、部门与正常／停用状态。 |
| 部门 Department | 企业内部树形组织，不是独立租户，也不自动授予数据权限。 | 支持新增、改名、调整上级、删除空部门。成员暂归属一个部门；同级名称不重复。 |
| 企业角色 Role | 所有者、管理员、成员；控制企业级管理操作。正式版本可按验证需求增加自定义角色。 | 预设角色、分配与目标权限矩阵；尚无实际鉴权。 |
| 资源授权 Resource grant | 对伙伴、项目、知识和成果的可见、使用、编辑、管理范围；独立于部门结构。 | 已有项目参与人和共享伙伴目录，无真实资源访问控制。 |
| 生态绑定 Integration binding | 归属企业的外部连接，关联一个伙伴与拟申请能力；同伙伴可绑定多平台。 | 现有绑定与消息执行演示保留，不因企业信息编辑而重写。 |

正式数据关系建议：`User → Membership(tenantId, userId, roleId, status) → Department`；部门包含 `tenantId, parentId`。所有业务资源必须归属 tenantId。全局用户身份不直接等同于企业成员身份；现有本地成员记录不能当作已经创建了真实账号。

## 角色与资源范围

| 操作 | 企业所有者 | 企业管理员 | 成员 |
| --- | --- | --- | --- |
| 企业资料、部门与成员管理 | 允许 | 允许 | 无 |
| 分配管理员／成员角色 | 允许 | 允许 | 无 |
| 所有权转移 | 允许，独立流程 | 无 | 无 |
| 配置共享伙伴和生态连接 | 允许 | 允许 | 无 |
| 使用伙伴、项目与成果 | 授权范围内 | 授权范围内 | 授权范围内 |
| 企业审计和用量 | 允许 | 允许 | 无 |

企业管理权限不意味着自动读取所有业务内容。正式产品按“有效成员 + 当前租户 + 操作权限 + 资源授权 + 外部平台授权”联合判断。项目内负责人、编辑者、查看者等细分授权在后续场景中定义；不要把“任务负责人”和“企业所有者”混为一种角色。

当前角色矩阵展示目标产品规则，成员停用只改变演示状态，不能撤销真实会话或阻断当前原型操作。UI 隐藏按钮也不能替代服务端鉴权。

## 与飞书、企业微信的关系

- 飞书、企业微信是生态连接，不承担 WorkX 租户和成员管理的唯一来源。一个企业可连接多个平台，同一伙伴可有多个绑定。
- 外部用户按“平台 + 企业标识 + 外部用户标识”建立显式身份映射，不按姓名自动合并跨平台用户。
- 接收消息时，先定位租户与绑定、核验触发身份和会话范围，再选择伙伴、检查可用工具与资料范围，生成归属该租户的任务。
- 伙伴执行不能扩大原始调用者或连接所具备的权限；回传始终使用任务来源的绑定与会话。企业成员角色不等于飞书或企业微信已授予的权限。
- 停用成员后的任务归属、进行中任务处理及交付接管需形成正式策略；停用或撤销平台绑定后不得继续使用失效凭证。

## 当前原型可验收内容

1. 团队空间显示企业名称与空间标识；编辑名称后刷新保留，现有任务、伙伴和绑定不变。
2. 组织架构可以建立多级部门；改上级时排除自己与下级，提交时再次校验，不能形成循环。同级部门不允许重名。
3. 有下级或成员的部门不能直接删除；移出后可删除空部门。
4. 成员可调整姓名、部门、角色与状态；所有者不能通过该表单降级或停用。新成员默认正常、未分配部门。
5. 角色与权限页展示三种预设角色的权限与资源范围，并明确尚未接入真实权限校验。
6. 企业管理变更写入本地协作动态。中英文界面均可查看；用户输入的企业与部门名称保持原文并安全转义。

## 正式 SaaS 首版验收要求（待建设）

| 编号 | 范围 | 验收要求 | 优先级 |
| --- | --- | --- | --- |
| SF-01 | 租户生命周期 | 创建企业、加入企业、切换当前企业；状态管理与离开／转移所有权有独立流程。 | P0 |
| SF-02 | 登录与成员生命周期 | 注册或企业 SSO、邀请接受、重复邀请处理、加入与停用；停用撤销会话与权限。 | P0 |
| SF-03 | 服务端权限 | 角色操作与资源范围在 API 和后台执行器一致校验；不依赖前端传入的角色或 tenantId。 | P0 |
| SF-04 | 全链路租户隔离 | 数据库查询、文件、缓存、搜索／向量检索、任务队列和消息回传均带可信租户上下文。用两个租户验证列表、详情、直接 ID 访问、导出和异步任务不串数据。 | P0 |
| SF-05 | 外部身份与授权 | 飞书／企业微信连接及凭证归属租户，外部身份显式映射，按调用者和授权范围执行。凭证加密存储、脱敏和撤销。 | P0 |
| SF-06 | 审计 | 记录操作者、租户、对象、动作、结果与时间；管理变更和敏感访问可追溯，不记录原始密钥。 | P0 |
| SF-07 | 用量与配额 | 按租户统计模型／任务用量，限制并发与额度，超额有明确反馈。 | P1 |
| SF-08 | 订阅与商业化 | 套餐、席位、账单、续订及到期策略按商业模式确认后建设；与当前原型演示统计分离。 | P1 |
| SF-09 | 企业高级治理 | 自定义角色、多部门成员、组织同步、审计导出及平台运营后台按需求验证投入。运营管理员与客户企业管理员分离。 | P2 |

SaaS 是交付和运营模式，不等于“有用户、组织和角色”就已完成 SaaS。首版以租户、成员、组织、预设 RBAC 和资源范围为基础，再接入真实执行与生态服务。

参考：[Microsoft SaaS 与多租户架构](https://learn.microsoft.com/en-us/azure/architecture/guide/saas-multitenant-solution-architecture/)、[AWS 多租户 SaaS 授权与 API 访问控制](https://docs.aws.amazon.com/pdfs/prescriptive-guidance/latest/saas-multitenant-api-access-authorization/saas-multitenant-api-access-authorization.pdf)。以上是 WorkX 的产品设计取舍，并非原样复刻某平台的角色规则。
